1. `_effective_root()` 只认 `media_type`（电影/电视剧）+ priority 取第一个，且显式 `download_root` 优先 → 下载侧完全无分类；

5. 前提缺口：14 条分类规则全部依赖 TMDB 字段（`media.genre_keys`、`extensions.themoviedb.origin_country`/`original_language`），**没有一条**引用 `extensions.lunatv.cms_class_names` 等 CMS 事实 → 若不先做 TMDB 富化，分类会落到「未分类」。

**容器内验证宿主逻辑的方法（本次新掌握，很实用）**：`app.factory.create_app()` 可引导，但 `get_configured_system_config()` 仍报「系统配置服务尚未配置」→ **monkeypatch `DirectoryHelper.get_dirs = staticmethod(lambda: [TransferDirectoryConf(**d) for d in db Directories])`** 即可跑通全部目录匹配；`MediaInfo` 在 `app.domain.context`（**不是** `app.schemas.media`）；`TransferDirectoryConf` 在 `app.schemas.system`；分类快照用 `app.application.classification.reference.persisted_classification_snapshot/apply_persisted_classification_snapshot`；策略读 `systemconfig['MediaClassificationPolicy']['active']`（嵌套在 `active` 下，不是顶层）。

### ⭐ 关键发现（v1 的致命缺陷）

1. **`src_path` 收窄陷阱**：`directory.py:449 matching_dirs = [d for d in dirs if src_path.is_relative_to(d.download_path)]` —— 只要下载根落在某个已配置下载目录内，候选就**只剩那一个目录**；分类/类型不符 → `get_dir` 返回 None → `module.py` 抛「未找到有效的媒体库目录」**拒绝整条整理**。

   ⇒ **v1「不传 target_path 交给宿主自算」是错的**；必须**显式传 `target_directory = get_dir(media)`**（`execution.py:575 if not task.target_directory` 短路，绕开收窄）。
   （附带：用户清空 `download_root` 后 `_effective_root` 会取到「国漫」下载目录 → 走 v1 方案会**全线拒绝整理**，比现状更糟。）
2. **`target_directory` 的两个空值炸弹**（`module.py:466-503`）：`library_path` 为空 → 抛 ValueError；`transfer_type` 为空 → 抛「未设置整理方式」。⇒ 插件必须先过滤 `library_path` 非空 + `transfer_type or "move"` 兜底。
3. **`scrape=False` 会覆盖用户目录的刮削设置**（`module.py:479 need_scrape = target_directory.scraping if scrape is None else scrape`）⇒ 必须传 `None`。
4. **`MediaInfo(tmdb_info=payload)` 的身份投影陷阱**：`__post_init__` 会用 `tmdb_info` 重投影身份与事实，**payload 里没有 `"id"` 时 `media_source`/`media_id` 被清成 None** → `build_classification_facts` 抛「分类事实要求完整的 media_source 与 media_id」→ `state=not_evaluated`（不报错、静默无分类）。⇒ 用宿主 `recognize_media()` 的返回对象，别自己拼。
5. **识别必须"不强制 TMDB"**：v1 强制 TMDB 源，未配 TMDB 的用户将**完全放弃整理**。改为三级取源（宿主已有身份 → 宿主按自身配置的源识别 → 插件 TMDB 关联）。
6. **`monitor_type=None` 的目录会被 `get_dir` 跳过**：9 套形态中 S3（全 None）恒返回 None。方案加了第二跳 `get_dir(media, include_unsorted=True)`（严格优于旧的"按目录名猜"）。
7. **`media is None` 时禁用 `get_dir`**：`media_match_rank(media=None)` 直接返回 3，所有目录同级 → 会按 priority 选中「动画电影」（本机 priority 0）→ **错归**。
8. **下载侧语义实证**：`get_download_dir_by_save_path(media, save_path)` 仅当 save_path **精确等于某个配置下载目录的根**时命中，再 `build_media_download_path` 追加分类；未注册根/子目录/固定分类目录 → 不命中，原样使用（宿主原生语义）。⇒ 下载侧只在能低成本拿到 media 时分类，其余保持旧语义；想"下载区也分类"就把 `download_root` 指向已配置的下载目录根。
9. **改策略/目录立即生效**：`recognize_media` 每次都跑 `finalize()`（`refresh` 参数被忽略），缓存命中的识别结果也会重新分类，不会带旧分类。
10. **无分类不丢文件**：分类为空时 `get_dest_dir` 因 category 空落到媒体库根；fork `_degrade_missing_category_to_root` 同理。

## 六、LunaTVSource「下载异常自动换源」能力审查（只读，无改动）

**结论：不支持。** 失败后只置 `state=failed` + 通知，重投**沿用同一个 URL**。
详见 `.workbuddy/luna-换源能力审查.md`。

### 现存的"重试/冗余"都不是换源（易误认）
- `downloader.py:2194` m3u8 列表获取 `range(2)`：同 URL，仅 408/425/429/5xx/超时/连接错可重试（**403 不可重试** → 单次执行直接失败）。
- `m3u8_engine.py:1319` `--download-retry-count 3`、`:195 DOWNLOAD_CONNECT_ATTEMPTS = 3`：同 URL 分片重试。
- `downloader.py:1651 for engine in self._m3u8_engines`：多引擎回退**骨架**，但 `:466` 只注册 `N_m3u8DLEngine` 一个 → 实际无回退。
- `downloader.py:3052/3085 range(2)`：**写库重试**，与下载无关。
- `__init__.py:5540-5567` + `:6764 _rank_subscription_results`：**下载前**的跨源择优（实测分辨率），不是失败后换源。
- `fallback_sources.json`：源**清单**的离线兜底，不是"下载失败换源"。
- `downloader.py:1685` 日志「using ffmpeg」是**遗留误导文案**，FFmpeg 只是混流依赖。

### 为什么失败任务复用不会变成换源 ⭐
`enqueue()`（`downloader.py:2947-2998`）能把 failed 任务重置为 pending 并写新 URL —— **但前提是"下次扫描找到同集另一个 URL"，而该前提不成立**：
- `_rank_subscription_results` 排序键 = `新季 > 集数 > 分辨率 > 原始顺序`，**完全确定性，不含失败/已试 URL 因子**；
- `source_strategy="first"`（默认）在 `:5507-5513` **直接截断为 1 条** → 备选源的 URL 在这里就被丢了。
⇒ 每轮算出同一名次、选中同一源、同一 URL；失败多少次都不改变。
- `attempts` 只在 `:1094`/`:2895` 自增，**从不与阈值比较** → 无"试 N 次放弃"机制。

### 线上实证（`plugindata.download_tasks_v1`，126 条：completed 124 / failed 2）
| 任务 | 源 | attempts | URL 主机 | 错误 |
|---|---|---|---|---|
| 巴比伦柏林 S05E01 | 🎬电影天堂 | **31** | play.phimgood.com | HTTP 403 |
| 巴比伦柏林 S05E02 | 🎬电影天堂 | **9** | play.phimgood.com | HTTP 403 |

**重试 31 次仍是同一主机** = 无换源的铁证。同 identity 多任务分组数 = 0（印证当前不产生重复任务）。
- **换源本可救**：全源扫描 17 个源有该剧，其中 **🎬如意资源也有 S05（更新至第02集）**，播放主机 `svip.ryplay14.com`（另一套 CDN）。
  打平后按原始顺序取靠前的电影天堂 → 永远选中失败源。

### 若要实现换源（改动点）
1. `__init__.py:5507-5513` 截断**之前**建 `(TMDB身份,season,episode) → [全部源 URL]` 候选表；
2. `__init__.py:5630-5659` 把候选写入 `DownloadTask.alt_urls`；
3. `downloader.py:268-338` 增 `alt_urls` / `failed_urls`（老记录给默认值，仿 `download_engine` 的兼容写法）；
4. `downloader.py:3220-3257 _finish_failed`：URL 记入 `failed_urls`，还有候选则重排 pending 换 URL，否则才终态 failed；
5. `downloader.py:2947-2998 enqueue()`：复用失败任务时从 `alt_urls - failed_urls` 取下一个候选，而非照抄同一 URL。

**实现前提（重要）**：默认 `source_strategy="first"` 时 `source_key = PLUGIN_MEDIA_SOURCE`（固定）+ `media_id` 用 TMDB 身份
⇒ `identity_key` **源无关**，天然能承载"同集换源且不产生重复任务"。
但 `"all"` 模式下 `source_key = result.source_key`（`:5640-5645`）→ 不同源 = 不同任务，**换源逻辑须限定只作用于 `first`**。
**另一方向**：403 出在播放 CDN 首次探测，热链保护（缺 Referer）是常见成因 → 带源 `detail` 域名为 Referer 可能比换源更根治，建议先实测。
